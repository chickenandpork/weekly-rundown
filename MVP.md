# Weekly Rundown MVP Technical Design

## Overview

This document outlines the technical design for the Weekly Rundown MVP (Minimum Viable Product). The system is a Slack-powered weekly project tracking service that allows teams to record daily project updates and generates weekly summaries.

## Architecture

### System Components

1. **Core Service** - Go-based HTTP server with SQLite database
2. **Slack Integration** - Slash command handler for note recording
3. **Database Layer** - SQLite storage for notes and tags
4. **Parsing Engine** - Text parsing for key-value extraction and tagging
5. **Weekly Summary** - JSON endpoint for weekly report generation

### Deployment Architecture

```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   Slack App     │    │   Weekly Rundown│    │   SQLite DB     │
│   (Slash Cmd)   │───▶│   Service       │───▶│   (Persistent)  │
│                 │    │                 │    │                 │
└─────────────────┘    └─────────────────┘    └─────────────────┘
```

## Implementation Details

### 1. Database Schema

The database schema is designed to store notes with proper indexing for efficient querying:

```sql
CREATE TABLE IF NOT EXISTS notes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at INTEGER NOT NULL,
    user_id    TEXT NOT NULL,
    user_name  TEXT NOT NULL,
    channel    TEXT NOT NULL,
    text       TEXT NOT NULL,
    tags       TEXT NOT NULL DEFAULT ''
);

CREATE INDEX IF NOT EXISTS idx_notes_created ON notes(created_at);
CREATE INDEX IF NOT EXISTS idx_notes_tags    ON notes(tags);
```

### 2. Note Storage and Retrieval

#### Insertion
- Notes are stored with timestamp, user details, channel, raw text, and tags
- Tags are serialized as comma-separated key=value pairs
- All fields are properly escaped to prevent SQL injection

#### Querying
- Weekly summaries are generated by querying notes within a 7-day window
- Results are ordered by creation time (newest first)
- Support for filtering by tags and users

### 3. Text Parsing and Tagging

The parsing engine extracts structured information from raw note text:

#### Supported Formats
1. `project:AAA,status:blocked` - key:value pairs
2. `project AAA blocked, needs review` - keyword extraction
3. `blocked, project AAA` - mixed formats

#### Tagging Logic
- Key-value pairs are parsed and stored as `key=value` tags
- Keywords are extracted and tagged as `status=keyword`
- Tags are normalized to lowercase for consistency

### 4. Slack Integration

#### Slash Command Endpoint
- `/weeklyrundown note <text>` - Records a new note
- Validates Slack command token for security
- Returns immediate confirmation to Slack

#### Response Format
```json
{
  "text": "Note recorded: [cleaned text]"
}
```

### 5. Weekly Summary Generation

#### Time Boundaries
- Weekly reports are generated for the current ISO week (Monday to Sunday)
- Start time is set to Monday 00:00:00 of the current week
- End time is set to the following Monday 00:00:00

#### Response Format
```json
{
  "notes": [
    {
      "id": 1,
      "created_at": "2026-06-29T10:30:00Z",
      "user_id": "U123456789",
      "user_name": "john.doe",
      "channel": "project-alpha",
      "text": "project AAA blocked by BBB",
      "tags": "project=aaa,status=blocked"
    }
  ],
  "total": 1,
  "since": "2026-06-22",
  "until": "2026-06-29"
}
```

## API Endpoints

### 1. Slack Command Handler
- **Path**: `/slack/command`
- **Method**: `POST`
- **Purpose**: Handle Slack slash commands
- **Security**: Validates Slack command token
- **Response**: Immediate confirmation to Slack

### 2. Health Check
- **Path**: `/health`
- **Method**: `GET`
- **Purpose**: Service health status
- **Response**: JSON with status and version

### 3. Weekly Summary
- **Path**: `/weekly`
- **Method**: `GET`
- **Purpose**: Retrieve weekly note summary
- **Response**: JSON with notes and metadata

## Security Considerations

### Authentication
- Slack command token validation prevents unauthorized use
- No user authentication required (Slack handles this)

### Data Protection
- All database fields are properly escaped to prevent injection
- No sensitive data is logged or exposed in responses
- Database is stored in a persistent volume for durability

### Rate Limiting
- No built-in rate limiting (rely on Slack's rate limits)
- HTTP server has timeout configuration to prevent hanging requests

## Performance Considerations

### Database Optimization
- Indexes on `created_at` and `tags` fields for fast querying
- Efficient query pattern to minimize database load
- In-memory database for development testing

### HTTP Server Configuration
- Read timeout: 10 seconds
- Write timeout: 10 seconds
- Idle timeout: 120 seconds
- Graceful shutdown on SIGTERM/SIGINT

## Known Limitations

### Current Constraints
1. **Single User Context** - Only supports Slack user context
2. **Basic Tagging** - Limited to key=value and status extraction
3. **No User Management** - No concept of user roles or permissions
4. **Simple Time Windows** - Only supports weekly reporting

### Performance Limitations
1. **Database Size** - Large datasets may impact query performance
2. **Memory Usage** - In-memory operations for small datasets only
3. **Concurrency** - Limited to single-threaded database operations

## Conclusion

This MVP provides a solid foundation for a weekly project tracking system. It addresses the core requirements of recording daily updates via Slack commands and generating weekly summaries. The design is extensible to support future enhancements while maintaining simplicity and reliability for immediate use.

The implementation follows Go best practices, uses SQLite for simplicity, and provides proper security through Slack command token validation. The system is designed to be easily deployable in containerized environments and supports both Docker Compose and Kubernetes deployments.
